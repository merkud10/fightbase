# Страницы сравнения бойцов (tale of the tape)

Дата: 2026-08-22. Статус: дизайн согласован, ждёт имплементации.

## Проблема

Перед боем читатель хочет видеть двух бойцов рядом: рост, размах, рекорд, ударная и
борцовская статистика. Сейчас для этого приходится открывать два профиля в соседних
вкладках и сравнивать глазами.

Поисковый спрос по шаблону «X против Y» сайт не закрывает вообще — таких страниц нет.
При этом все нужные данные уже лежат в модели `Fighter`: рекорд, возраст, рост, размах,
способы побед и 12 официальных метрик UFC.

## Решение (согласовано)

Новый раздел `/ru/compare/<slugA>-vs-<slugB>` с таблицей характеристик. В индекс идёт
только курируемый набор пар; любая другая пара открывается и работает, но отдаёт
`noindex, follow`.

### Не в объёме (явно)

- Интерактивный селектор произвольной пары — отложен. Он дорог (клиентский компонент
  плюс API поиска), а ведёт в основном к парам, которые всё равно `noindex`.
- Междивизионные пары и пары с ушедшими бойцами в курируемый набор не попадают
  (открываются, но не индексируются).
- Пары из pound-for-pound рейтинга — не в этой итерации.
- Прогноз исхода, вероятности, коэффициенты. Страница показывает факты, а не предсказание;
  за это отвечает существующий раздел `/predictions`.

## Курируемый набор

Объединение двух источников:

1. **Пары из таблицы `Fight`** — любой статус. Это реально состоявшиеся и назначенные бои,
   спрос по ним заведомо есть. Сейчас 73 записи.
2. **Ранкед-пары внутри дивизиона** — чемпион и топ-15 из последнего снимка
   `UfcRankingSnapshot`, попарно внутри своей весовой категории.

Пара включается только если оба бойца есть в базе и проходят `looksLikeLowQualitySlug`
из `lib/sitemap-entries.ts` — тот же фильтр дублей, что и в карте сайта.

**Источник рейтинга — сохранённый снимок, а не живой запрос.** `fetchUfcOfficialRankings`
ходит на ufc.com и по контракту возвращает `[]` при любом сбое (см. `tests/ufc-rankings.test.ts`).
Если строить набор на живом фетче, недоступность ufc.com обнулит раздел в sitemap.
При пустом снимке набор деградирует до пар из `Fight` — они есть всегда.

Ожидаемый размер: ~650 страниц. Считано по проду: 11 дивизионов, 118 ранкед-бойцов
с учётом пересечения с P4P, то есть примерно чемпион и топ-10 на дивизион — это ~55 пар
на дивизион. Если UFC начнёт отдавать полный топ-15, набор вырастет примерно до 1300;
верхнюю границу закладываем в расчёты, но не рассчитываем на неё.

## Канонизация URL

Слаги в пути отсортированы лексикографически: `/ru/compare/aljamain-sterling-vs-sean-omalley`.
Запрос с обратным порядком отвечает 301 на канонический — так пара имеет ровно один URL
и дубли не возникают.

Разбор пути: делим по `-vs-`. Слаг бойца теоретически может содержать эту подстроку, поэтому
при нескольких вхождениях перебираем все точки разреза и берём ту, где обе половины находятся
в базе. Если подходящей нет — 404.

404 также на: несуществующий слаг, сравнение бойца с самим собой, отсутствие `-vs-` в пути.

## Роут и рендеринг

- `app/compare/[pair]/page.tsx`, `revalidate = 3600` — как на остальных страницах.
- `generateStaticParams` не используем: сотни страниц на каждой сборке заметно её замедлят,
  а ISR сгенерирует страницу по первому обращению и дальше отдаст из кеша.
- `app/compare/(list)/page.tsx` — хаб, серверный, сгруппированный по дивизионам. Он же
  точка входа из главного меню.

Middleware уже обрабатывает префикс локали и переписывает `/ru/compare/...` → `/compare/...`,
менять его не нужно.

## Данные

Новый модуль `lib/db/comparison.ts`, переиспользующий `select` из `lib/db/fighters.ts`:

- `getComparisonPageData(slugA, slugB)` — оба бойца, их истории боёв, факт очной встречи
  (запись в `Fight` между ними) и предстоящий бой, если он назначен. Обёрнут в `cache()`.
- `getCuratedComparisonPairs()` — набор пар для sitemap и хаба. Обёрнут в `cache()`.

## Таблица характеристик

`components/compare-table.tsx` — серверный компонент. Строки: рекорд, возраст, рост, размах,
способы побед (KO/TKO, сабмишены, решения) и 12 метрик UFC.

Правила отображения:

- строка скрывается, если значения нет у обоих бойцов;
- если значение есть только у одного — у второго «—», подсветка не даётся никому;
- «кто лучше» подсвечивается по метрике.

**SApM (пропущенные удары в минуту) — единственная инвертированная метрика: меньше значит
лучше.** Остальные метрики — чем больше, тем лучше. Возраст и рост не сравниваются вообще:
преимущества там нет, только различие.

## SEO

- `buildPageMetadata` из `lib/page-metadata.ts`. Заголовок: «Ислам Махачев против Илии Топурии:
  сравнение бойцов UFC».
- JSON-LD: `BreadcrumbList` и два `Person`, через существующий `components/json-ld.tsx`.
  Отдельного schema.org-типа для сравнения не существует, выдумывать его не будем.
- В `app/sitemap.ts` добавляются только курируемые пары: `priority` 0.6, `changefreq` `monthly`.
  Для пар с назначенным боем — `weekly`.
- Некурируемые пары отдают `robots: { index: false, follow: true }` через `generateMetadata`.

## Точки входа

- Кнопка «Сравнить бойцов» на странице боя и в прогнозе.
- Блок «Сравнить с» в профиле бойца. **Ссылки ведут только на курируемые пары** — иначе
  профиль раздавал бы вес на `noindex`-страницы. Практически это значит: у ранкед-бойца —
  соседи по рейтингу в своём дивизионе, у любого бойца — соперники по записанным боям.
  Если курируемых пар нет (неранкед-боец без записей в `Fight`), блок не выводится вовсе.
  Так курируемый набор оказывается покрыт внутренними ссылками; без этого страницы
  из sitemap индексируются вяло.
- Пункт «Сравнение» в главном меню, ведёт на хаб.

## Тесты

- разбор и канонизация слага пары, включая путь с несколькими `-vs-`;
- редирект с неканонического порядка;
- выбор лучшего значения: обычная метрика, инвертированная (SApM), пропуск у одного
  и у обоих бойцов;
- правило курирования: пара включается только когда оба бойца существуют и не отсеяны
  как дубли; при пустом снимке рейтинга набор сводится к парам из `Fight`;
- блок «Сравнить с» не выводится, когда у бойца нет ни одной курируемой пары.

## Риски

- **Рейтинг приходит извне.** Снимок может устареть, если ufc.com долго недоступен. Набор
  при этом не ломается, а сжимается до пар из `Fight`; страницы, уже попавшие в индекс,
  продолжают работать.
- **Тонкий контент.** У части бойцов заполнены не все 12 метрик, и таблица окажется короткой.
  Курирование по рейтингу это смягчает: у ранкед-бойцов статистика заполнена лучше всего.
